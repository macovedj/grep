# Rust matcher: whole-command benchmarks

`run.py` compares two release builds of the same grep frontend: the default
Oniguruma backend and `--features rust-matcher` (with Oniguruma retained for
`-P`). These are complete, fresh-process CLI invocations, rather than matcher
microbenchmarks. Every invocation compiles its pattern, reads a generated file,
matches it, and generates output. Empty-file cases expose startup plus pattern
compilation; they do not isolate compiler CPU time.

The optional GNU executable supplies black-box correctness observations only.
Its performance is not measured. No GNU implementation source or tests are
read, copied, or linked into these builds. All fixtures are generated by this
harness.

## Reproduce

Python 3 and a Rust toolchain supporting the project are sufficient. Build both
binaries from the same checkout, lockfile, compiler, and release profile. For
example, in a POSIX shell:

```sh
cargo build --locked --release --bin grep \
  --target-dir target/bench-default
cargo build --locked --release --bin grep --features rust-matcher \
  --target-dir target/bench-rust

python3 benchmarks/rust-matcher/run.py \
  --baseline target/bench-default/release/grep \
  --candidate target/bench-rust/release/grep \
  --gnu /usr/bin/grep \
  --source-commit "$(git rev-parse HEAD)" \
  --rustc "$(rustc --version --verbose)" \
  --rounds 9 --warmups 2 --timeout 2 \
  --output target/rust-matcher-bench.json
```

Use an actual GNU grep path for `--gnu`, or omit that argument. On systems where
`/usr/bin/grep` is another implementation it is not a GNU reference.

The script creates deterministic temporary files and deletes them on completion.
It validates exit status and exact stdout SHA-256 before timing, recording
stderr separately. Timed invocations discard stdout and collect then discard
stderr; successful cases emit no stderr. It alternates the two builds' order,
warms each twice, records nine samples, and reports median and range. Every
child has its own timeout. Locale and relevant grep environment settings are
set per child. The JSON retains binary, lockfile, harness and input hashes,
commands, compiler/platform metadata, observations and raw timing samples.

A candidate/baseline ratio is reported only when exact stdout and status agree,
the exit status is 0 or 1, and timed runs retain that status without timeouts.
When GNU is supplied, both builds must also agree with its stdout and status.
The optional GNU observations still distinguish agreement between the two
builds from agreement with GNU. Expected errors and known wrong answers remain
visible in the JSON; harness completion does not mean all comparisons passed.

## Recorded macOS arm64 run

[`results-macos-arm64.json`](results-macos-arm64.json) was measured on
2026-10-23, Darwin 27.0.0 arm64, 18 logical CPUs, Python 3.13.2, Rust
1.98.0-nightly (`31a9463c6`, 2026-05-25), with GNU grep 3.12 as the oracle.
Both binaries were built from `94f5d71d35de3caaf1c712c0a726680b3d83cf80`
with the same lockfile and `cargo build --locked --release`; the candidate adds
`--features rust-matcher`. The release profile uses fat LTO, one codegen unit
and aborting panics. No engine changes were made for these measurements.

Median whole-command milliseconds follow. The ratio is candidate / baseline;
lower is faster. All 17 rows below agree with GNU in exact stdout and status.

| Case | Oniguruma ms | Rust ms | Ratio |
| --- | ---: | ---: | ---: |
| Empty file, simple pattern | 3.94 | 3.97 | 1.01 |
| Empty file, 128-branch expression | 4.23 | 17.00 | 4.02 |
| Empty file, bounded Unicode word expression | 4.67 | 55.40 | 11.86 |
| ASCII match count, 8.9 MB | 18.00 | 10.88 | 0.60 |
| BRE interval count, 8.9 MB | 16.23 | 13.91 | 0.86 |
| ASCII absent pattern, 8.9 MB | 11.22 | 12.76 | 1.14 |
| Short lines, 5.4 MB | 76.53 | 17.11 | 0.22 |
| One long match with `-o`, 1 MiB | 16.31 | 6.89 | 0.42 |
| Repeated alternations with `-o`, 1.05 MB | 87.70 | 16.52 | 0.19 |
| Unicode word count, 2.56 MB | 16.98 | 10.14 | 0.60 |
| Unicode words with `-o`, 2.56 MB | 135.94 | 36.90 | 0.27 |
| ASCII ignore-case count, 7 MB | 56.83 | 15.79 | 0.28 |
| Unicode ignore-case count, 1.84 MB | 14.42 | 6.42 | 0.45 |
| Fixed-string count, 8.9 MB | 5.20 | 5.66 | 1.09 |
| Successful backreferences, count, 200 kB | 5.07 | 4.42 | 0.87 |
| Successful backreferences with `-o`, 200 kB | 13.40 | 8.85 | 0.66 |
| Absent backreference, 1 kB | 4.80 | 4.49 | 0.93 |

Three additional observations deliberately do not receive performance ratios:

- `(a|aa)+\1` on 28 `a` bytes plus newline: Oniguruma and GNU return a match;
  Rust returns status 2 after its backtracking budget is exhausted. Its 18.25 ms
  error is not a successful search speedup over Oniguruma's 19.66 ms match.
- C-locale `[[:alpha:]]` on repeated `E2 82 62 0A` bytes: GNU and Rust count
  10,000 lines containing `b`; Oniguruma incorrectly finds none. The two builds
  do different work and their timings are not compared.
- C-locale `(ab)\1` on `é abab`: Oniguruma and GNU print `abab`; Rust returns
  status 2 because of the documented non-ASCII fallback guard. That guard is a
  compatibility limitation, not a performance improvement.

No invocation timed out. The regular-expression throughput cases are promising,
but the 128-branch and bounded Unicode-word expressions show substantial new
startup/compilation costs. The byte-input guards and exponential backreference
case remain correctness limitations independent of throughput.

## Limits

These are synthetic warm-page-cache workstation measurements, without CPU
affinity, exclusive machine access, cold-cache trials, peak-memory measurement,
or statistical confidence intervals. Millisecond-scale differences can be
noise; raw ranges and all samples are retained rather than reduced to an
overall score. Redirecting output to a null device does not model terminal or
pipe backpressure. The builds share the existing CLI/search/output code, so
this isolates the practical effect of backend selection within that frontend.

The cases exercise both line-presence and span-enumerating paths, but are not an
exhaustive performance or compatibility suite. They do not establish that the
Rust backend is ready to become the default, nor that the observed ratios
generalize to Linux, Windows or WASI. The CI benchmark job publishes a separate
Linux report for comparison instead of treating these local numbers as portable.

## Lazy-DFA follow-up

The [follow-up report](../../docs/benchmarks/rust-matcher-lazy-dfa-macos-arm64.json)
compares two Rust-matcher release builds: the retained eager-DFA binary and the
local lazy-DFA change. Both use the recorded 1.98 nightly, lockfile, and fat-LTO
profile. Pass `--profile-description` to record these different build roles.

The harness now includes four additional bounded-Unicode cases, covering empty
input with `-o`, short matching input, and a 1.32 MB count/`-o` workload. These
check that reducing compilation cost benefits commands that actually match.
The original reports above retain their original 20 cases and source hashes.

In this local follow-up, bounded-Unicode empty-input startup falls from 51.15 ms
to 5.20 ms; the matching 1.32 MB `-o` case falls from 63.21 ms to 14.86 ms.
There are throughput tradeoffs: repeated alternations with `-o` increase from
12.78 ms to 14.28 ms, and the long-line `-o` case increases from 3.68 ms to
4.00 ms. All raw samples are retained. These remain local measurements;
updated Linux/Windows timing has not been collected.
